## 0. 执行摘要

### 0.1 结论摘要

1. **容量主结论（c=50 基准，即 50 亿点）**：2048 维下**单副本单代向量 51.84 TB**、**两副本两代 207.36 TB**；
   若按"两副本两代 + 30% 空闲"采购，**向量层约需 296.23 TB**。
   ⚠️ 这**只是向量层**，且**未计** payload/稀疏索引/日志/快照/构建临时/备份 —— **严禁**把它说成"全系统总容量"。
2. **元数据主结论**：PG 分段表按 **2.3 KB/段**估，c=50 时 **11.5 TB**（**不含**实测膨胀与副本）。
3. **原件层主结论**：500 TB 原件在 **EC 4+2 的理想编码系数 1.5** 下是 **750 TB**；单站点留 30% 空闲 →
   **约 1.0714 PB 原始盘**（不含版本化、元数据、暂存、备份）。**第二个完整站点按同口径单独计算**，不是把已有系数再乘一遍。
4. **吞吐主结论（c=50，50 亿点）**：全批次要在 **365 天**内完成 → 原件读取 **15.86 MB/s（0.127 Gbps）**、**3.17 文件/s**、**158.5 段/s**；
   要在 **30 天**内完成 → **192.9 MB/s（1.543 Gbps）**、**38.58 文件/s**、**1929 段/s**。
   这四条曲线（30/90/180/365）是后面所有扩容与采购的**输入**。
5. **分段数必须条件化**：`N_parsed = N_f × r_p × c`。**不能**由"500 TB"直接推出"50 亿点"——那是"平均 5 MB + 每文件 50 段"这一组假设的产物；
   平均文件 1 MB 时同口径变成 **259.2 TB**（单副本单代），差 5 倍。
6. **整改顺序**（§11）：先抽样定性 → 再验 2048 模型真就绪与基准 → 再有界可靠管道 → 再受限回填与向量写入 →
   再检索索引/冷热/缓存 → 再故障恢复与混合并发验收 → 最后按实测扩容。
7. **可靠性/治理/上线门槛全部保留**（原 14 项审查意见的处置见 §13），500 TB 与 2048 维**只是输入参数**，不改变工程门槛。

### 0.4 固定目标与硬边界（优化**不得自动降级**）

| 边界 | 允许 | **禁止** |
|---|---|---|
| **维度目标** | **2048 为固定交付目标**；1024 只作为"当前运行事实 / 迁移期并存代次 / 回滚对象"存在 | 自动降回 1024 交付；**截断维度**；"声明 2048、实际 1024"；以 2048 名义写 1024 向量 |
| **覆盖范围** | **全部"可处理资料"最终都必须覆盖到目标代次**；冷热只决定**缓存/驻留层**与**回填顺序** | 只向量化"热数据"来凑预算；把未处理资料**静默排除**；用抽样代替全量覆盖目标 |
| **冷热的含义** | 冷热 = **缓存/驻留层**（RAM/page cache/`on_disk`）× **回填与驻留顺序** | 把"冷"解释成"永久不处理/不覆盖" |
| **排除与部分处理** | 必须**显式统计并可见**：排除原因（不可解析/加密/超限/策略排除）、部分完成范围、剩余待处理量、目标代次覆盖率 | 把"未处理"计入"已完成"；用不同完成率口径掩盖缺口 |
| **预算压力** | 通过**分期、限速、排队、扩容**解决 | 通过**降维、降覆盖、放宽核验强度**解决 |

配套要求（与后文一致）：

1. **覆盖率核验的对象是"全部可处理资料"**：`新代点数 ≥ 期望（按可处理资料全量计算）`，并附**排除清单对账**（§7.2 VERIFY、§8.2）。
2. **排除清单与部分完成必须有独立台账**（原因码 + 数量 + 复核人/时间），并在验收时与"已完成"分开报告（§10.2、§14-18）。
3. 若因容量或窗口必须分期，**分期的对象是"批次顺序"而不是"覆盖范围"**——任何一期都不允许把"永久不处理"写进计划。

### 2.2 主表（**向量层**，2048 维，每点 8192+2048+128 = **10368 B**）

**通式（逐集合、逐状态求和；下表只是它的一个实例）**：

```
U_vec(stage) = Σ_{g ∈ 该阶段存活的集合} [ N_g × rep_{g,stage} × ( 4·d_g + (qz_g ? d_g·q_g/8 : 0) + h_g ) ]
             + U_payload + U_sparse + U_build_tmp + U_other
```
- `N_g` 该集合点数、`d_g` 该集合维度、`qz_g`/`q_g` 量化开关与位宽、`h_g` 图每点字节（**逐集合取值，不能抽成全局常数**）。
- **`rep_{g,stage}` 是该阶段该集合"实际存在（含正在补建）"的物理副本数**，不是稳态副本数：
  正常态 `rep_{g,normal} = rep_g`；**恢复期必须按实际存活 / 补建中的数量填**。
- **`U_payload`**（payload 字段与过滤索引）、**`U_sparse`**（稀疏/全文索引）、**`U_build_tmp`**（**索引构建临时盘，单列**）、
  **`U_other`**（WAL、快照）**必须单列**；下表的"**向量层**"口径**不含**这些项（见下方边界声明第 1 条）。
- **旧 1024 集合**若存在，按其**实际点数**作为一个集合计入 —— **不能**把它当成"2048 的两代"混算。

**三个阶段的清单与副本口径不同（**不得**用"集合并集"表达）**：

| 阶段 | 口径 | 规则 |
|---|---|---|
| 正常态 | `G_normal`，`rep_{g,normal} = rep_g` | 当前对外可查的全部物理集合（含旧 1024 存量集合） |
| 重建态 | 新增集合**逐项列出**：`G_new = {本次新建、且不属于 G_normal 的集合}` | 已在 `G_normal` 里出现的新代**不重复加** |
| 恢复态 | **按"实际存活 + 正在补建"的物理副本数 `rep_{g,state}`，逐集合 / 逐站点（节点）计峰值** | ① 把**已丢失副本补回目标副本数**，**不会**自动再加一套稳态容量（同一集合的同一份数据）；<br>② **旧盘保留 / 临时副本并存**，按**实际占用**加；<br>③ **恢复阶段不一定需要新建物理集合**（通常是补副本或重建已有集合） |

> 为什么**不能**写 `G_recovery = G_normal ∪ {需要补副本的集合}`：那是**集合级**的并集，**同名集合会被去重**，
> 算不出"副本少了几份 / 暂时多了几份"的字节差。恢复期容量必须落到 **`rep_{g,state}` × 每点字节 × 站点/节点** 上逐项相加。

| `c` | `N_parsed = N_vec` | 原向量 fp32（8192 B/点） | int8 附加（2048 B/点） | 图【假设】（128 B/点） | **单副本单代** | **两副本两代（×4）** | 两副本两代 + 30% 空闲（÷0.7） |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 20 | 2.0×10⁹（20 亿） | 16.384 TB | 4.096 TB | 0.256 TB | **20.736 TB** | **82.944 TB** | 118.49 TB |
| **50** | **5.0×10⁹（50 亿）** | **40.96 TB** | **10.24 TB** | **0.64 TB** | **51.84 TB** | **207.36 TB** | **296.23 TB** |
| 200 | 2.0×10¹⁰（200 亿） | 163.84 TB | 40.96 TB | 2.56 TB | **207.36 TB** | **829.44 TB** | 1184.91 TB |

**必须随表一起写的边界声明**：

1. 本表**只覆盖向量层**：**未计** payload 字段与过滤索引、稀疏/全文索引、WAL/日志、快照、构建临时空间、备份、审计，**也未计** PG 与原件层。
2. "÷0.7"的含义**仅是**"按 30% 空闲预留"的采购换算，**不是**任何形式的系统总容量；**严禁**表述为"全系统需要 X TB"。
3. `h=128 B/点` 是**假设**，必须实测；量化**不替换**原向量（fp32 与 int8 是**相加**关系）。
4. 单副本单代/两副本两代是**两种部署档**，不是"先买前者再翻倍"的承诺。

### 2.3 PG 分段表（按 2.3 KB/段）

| `c` | `N_parsed` | 分段表字节 | 说明 |
|---:|---:|---:|---|
| 20 | 2.0×10⁹ | **4.6 TB** | **不含**实测膨胀（索引/MVCC/TOAST）**不含**副本 |
| **50** | **5.0×10⁹** | **11.5 TB** | 同上（主情景） |
| 200 | 2.0×10¹⁰ | **46 TB** | 同上 |

> 口径：PG 分段表用 `N_parsed`（解析产物，**与是否向量化无关**：解析了但不向量化的正文照样占空间）；
> 向量与嵌入吞吐用 `N_vec`。两者**不得混用**。

### 2.4 敏感性：平均原件 1 / 5 / 20 MB（**c=50 固定**）

| 平均原件 | `N_f` | `N_parsed`(c=50) | 单副本单代向量（10368 B/点） | PG 分段表（2.3 KB/段） |
|---:|---:|---:|---:|---:|
| 1 MB | 5.0×10⁸ | 2.5×10¹⁰ | **259.2 TB** | 57.5 TB |
| **5 MB** | **1.0×10⁸** | **5.0×10⁹** | **51.84 TB** | **11.5 TB** |
| 20 MB | 2.5×10⁷ | 1.25×10⁹ | **12.96 TB** | 2.875 TB |

**结论**：**分段数必须条件化**——`N_parsed = N_f × r_p × c`，而 `N_f = B/s̄`。
**不能**由"500 TB"直接推出"50 亿点"；同是 500 TB，平均文件从 5 MB 变成 1 MB，向量层就涨到 **259.2 TB（5 倍）**。
所以 §11 第 1 步（分层抽样定性）是**一切容量数字的前置**。

**关于这张表的性质（重要）**：`s̄` 与分段密度 `c` **在真实语料中是相关的**（格式、来源、扫描质量同时影响两者），
所以本表**固定 `c=50` 只是为了把它当"控制变量"**、单独观察 `s̄` 的影响 —— **不是**断言现实中 `c` 不变。
真实的 `(s̄, c, r_p, r_v)` 必须**在真实样本上按分层联合估计**：先按"格式 × 来源 × 大小分桶"分层，
每层分别估出这四个量的均值/分位数与样本量，再按预期混比加权汇总，并报告置信区间与离群层。
因此本表的 12.96 TB ~ 259.2 TB 是**敏感性区间（上下界）**，**不是预测值**，更**不能**取其中一档当采购依据。

### 2.5 原件层（对象存储）

```
理想数据编码字节 = B × k_ec = 500 TB × 1.5 = 750 TB        # EC 4+2 的**理想**编码系数
单站点采购下限   = 750 TB ÷ (1 − 30%) = 1071.43 TB ≈ 1.0714 PB 原始盘
```
- **不含**：版本化历史与未回收旧版本、对象元数据、暂存（staging）、备份/归档、审计、以及跨站点流量开销。
- **第二个完整站点**：按**同一口径单独计算**（该站点自己的 EC/副本策略 + 自己的空闲比例），
  **不得**在已含 `k_ec` 的数值上"再乘一个 1.5/2"（那是重复计；不同站点用该站点自己的物理字节值求和）。
- EC 4+2 的 1.5 是**理想编码系数**，不含重建期间的临时开销与热备盘；**不是采购承诺**。

### 2.6 源数据盘与峰值口径（源 + staging + final）

| 路径 | 盘占用口径 | 需列清的边界 |
|---|---|---|
| A 源盘复用（只读保留） | 源盘**原样保留**；对象存储只存 final | 源盘是否可长期只读挂载、是否与业务共用、故障域是否与 final 相同 |
| B 复制到对象存储后保留源只读 | 峰值 ≈ 源盘 + final（**并存期**） | 并存期多长、何时可回收源盘、回收是否可逆 |
| C 重新上传（源不可用/不可信） | 峰值 ≈ staging + final；源盘不参与 | 上传带宽与窗口、断点与幂等、校验通过前不发布 |

```
峰值占用 ≈ 源盘(若并存) + Staging(有界) + Final(committed)

【Staging 的硬上界（**不是**"平均大小 × 并发数"的估算）】
  受理规则  : 声明大小 > 单文件大小上限 → **直接拒绝**（**不得**用 min 裁小预留后继续受理）
              声明大小**未知** → **按单文件大小上限预留**
  单会话预留: reserved_object = (声明大小 或 上限) × f_s_max      # f_s_max = 该格式的解压/膨胀比上限（白名单；超限即拒绝）
              reserved_tmp    = 该格式的解析临时配额上界
  两条独立硬帽（**各自原子预留**；**实际字节不得超预留**；不足即拒绝 429/503，**扩额后才准继续写**）：
              Σ_{在途会话} reserved_object_bytes ≤ **ObjectStagingCap**
              Σ_{在途会话} reserved_tmp_bytes    ≤ **ParseTmpCap**
  回收（**任务终止 ≠ 占盘释放**）：
              取消/超时 → 先 **fence 旧写入者**、停止写入 → 待**实际删除完成或确认对象已回收**，才释放占盘预算
              清理失败 → **保留占用计费 + 重试**（不得因"任务已结束"就记账释放）
              **对象生命周期规则不能替代实时硬帽**（它只兜底遗留对象，不参与准入判定）
  分预算    : U_stage = U_staging_objects + U_parse_tmp      # 原件暂存盘与解析临时盘**分开配额**，不互相挤占
  示例（**仅"连续运行"的期望值，不保证最大值**）：200 MB/s × 4 h ≈ 2.88 TB；
      长尾大文件/高膨胀文件会突破"并发数 × 平均件大小"——上界由 **两条 Cap + 预留机制**给出，**不是**由平均值给出

【硬帽必须由"**实际对象写入端能力**"共同执行（**PG 预留本身不构成物理硬帽**）】
  为什么：① 直传 URL **可重放**；② **版本化桶**下同 key 重复 PUT **会新增物理版本**；
          ③ **PG 会话 CAS 只约束"业务受理"，约束不到对象盘的真实字节** —— 所以仅靠 PG 预留**不能**保证物理硬帽。
  三项执行手段（须齐备；缺任何一项就改受控上传入口）：
    1) staging **唯一 key 的条件创建**：`If-None-Match: *` —— **该后端是否支持必须实测**；不支持就**不得**依赖它去重/防覆盖；
    2) **multipart / 重试逐次预留**：每个 part 与**每一次重试**都要**单独预留并计入**在途额度；
    3) 计入**未完成分片**（未 `CompleteMultipartUpload` 的 parts）与**全部未回收版本**，
       直到**实际回收确认**才释放（与上文"回收"条款一致）。
  兜底：若目标 **S3/MinIO 后端无法强制约束**（不支持条件写、生命周期/桶策略无法限制版本与分片、无桶配额），
       **必须**改为**受控上传入口**（字节经服务端中转，由服务端逐次预留并执行上限）或**其他可执行配额方案**；
       **不得**宣称"仅靠 PG 会话预留即可保证物理硬帽"。
```
**硬约束**：**暂存按在途预算有界，禁止全量 500 TB 预拷**；staging 前缀设短生命周期与配额（§4.3/§4.4）。

### 2.7 逐站点 / 逐层容量校验（η 是比例）

```
对每站点 s、每存储层 l（对象 / PG / 暂存 / 向量）：
    U_peak[s,l] ≤ Capacity[s,l] × (1 − η[s,l])
    采购下限：Capacity[s,l] ≥ U_peak[s,l] / (1 − η[s,l])
预算摘要 = Σ_{s,l} Capacity[s,l]     # 只是摘要：不同层的盘不可互换（向量盘空闲不能顶替 PG 盘）
```
- `U_peak` 是**去重后的实际峰值占用字节**（含重建/快照/构建临时的峰值，不与其他项重复计）。
- **不做的事**：不再加一遍总量（主站点已在其中）；已按 `k_rep`/`k_ec` 计过的副本不重复加；
  **WAL 重放不计入磁盘增量**（它是 IO/时间工作量，除非落成新持久副本或新增归档保留）。

### 2.9 扩容公式（利用率/可用时长/重试/增量/在线预留）

```
【1) 先算可用的**批次写入窗口**（**不能**直接用全日历 T）】
  W_ingest = (T_days − T_build_days − T_validate_days − T_catchup_days) × 86400     要求 **W_ingest > 0**
  λ_batch  = N_vec / W_ingest                    # 批处理实际必须达到的嵌入速率（段/s）
      （只有"导入与构建并行"**被实测证明**时，才可另算重叠后的等效窗口；未证明就按上式保守扣减）
  §2.8 那张表仍是 **W = T（全日历）的理论下限**，**不是最终选型输入**；**选型一律用 `λ_batch`**。

【2) 实例数下界（**向上取整**）】
  n ≥ ceil[ (λ_batch + λ_new) × (1 + ρ_retry)
            ÷ ( q_inst × u_time × u_util × (1 − ρ_online) ) ]

  λ_new    **新增到达率**（段/s）：必须**显式给出**；**不得**把"年增长率 × 存量"直接当实时倍数
           （增长率是年度口径，要与存量、在线服务时长、批处理窗口分开展开算）
  q_inst   实测单实例嵌入吞吐（段/s，必须基准测试）
  u_time   每日可用时长比例（维护/重启/抢占扣除）
  u_util   目标利用率（建议 ≤0.7，与排队论一致）
  ρ_retry  **额外尝试工作量 ÷ 成功基线**（**不是**失败概率）；若把失败概率记为 p，
           则"独立无限重试"的期望尝试次数是 1/(1−p) —— **两种口径不得混用**
  ρ_online **只计"与该实例共享资源"的在线负载**；**无共享时取 0**
           （例如向量库检索预留**不能**直接扣到一台独立 GPU 的实例上）
```

**必须分开的两个口径**（不得互相替代）：

| 口径 | 含义 | 证据要求 |
|---|---|---|
| **A. embedding 基准** | 纯嵌入吞吐（段/s、tokens/s）、批大小与序列长度曲线、显存占用 | 服务端自报 + 客户端实测双份 |
| **B. 端到端"可检索"完成** | 原件读取 → 解析 → 分段写盘 → 嵌入 → 向量写盘 → **索引构建** → 核验 → 可检索 | 逐阶段时长与最终"可检索"状态（§7.3 HNSW 三态） |

> B 才是交付口径。A 快而 B 慢是常态（索引构建、PG WAL、对象带宽各自成为瓶颈，§8.4）。

### 2.10 OCR 页吞吐（单列瓶颈，不能只算 GPU）

OCR 比例与平均页数**未知**【待实测】，因此 OCR **必须单列**：

```
所需 OCR 页/s = (待处理原件数 × OCR 命中率 × 平均页数) / (T×86400)
页吞吐能力   = 实测页/s × 实例数 × u_time × u_util
```
OCR 的瓶颈可能在 **CPU / 子进程 / 图像解码 / 临时盘**，**也可能在 GPU**（视觉 OCR 常与嵌入**共享实例与显存**）——
**不存在"OCR 与嵌入天然不共享资源"的假设**：必须按**实际资源池**（CPU / GPU 显存 / 模型实例 / 网络 / 临时盘）分别做**隔离与预算**，
并实测"OCR 与嵌入并发"时的相互降级。若 OCR 命中率高，页吞吐可能先于嵌入成为瓶颈（§8.4、§11 第 1 步先测比例与页数）。

### 2.11 明确不承诺

- 不承诺 GPU 卡数（§2.9 只给公式与待填参数）。
- 不承诺 2048 维"一定更准"（召回必须实测，§1.3）。
- 不承诺"上表之和就是全系统容量"（§2.2 边界声明）。
- 不承诺并发数字（§10.4）。

### 3.2 组件与故障域

| 组件 | T2 形态 | 故障域 | 单点失效后果 | 必须的冗余 |
|---|---|---|---|---|
| 入口 | **≥2 代理/LB（跨主机或高可用托管入口）** + 多 web 副本 | 代理 / web 主机 | 单代理即单点 | ≥2 代理跨故障域 + 健康摘除；web ≥2 副本 + 共享会话 |
| 应用状态 | 会话/缓存入 Redis（会话当前在 PG） | Redis 主机 | 会话丢失、限流闸门失效 | Redis 主从/哨兵；失败时不放开限流（fail-closed）；**与 broker 隔离** |
| 任务派发（broker） | Redis 或独立 broker | broker 主机 | 任务停发、回执丢失 | **broker 单点恢复 + outbox 重放**（§4.4）；不与缓存/会话共用同一资源池 |
| 元数据 | PG 主备 + 只读副本 | PG 主机 | 写全停 | 流复制 + 自动切换（**共识/见证 + fencing 防双主**）+ PITR |
| 向量 | Qdrant N 分片 × R 副本，**跨物理主机** | 节点 | 该分片不可查 | 副本 ≥2 跨故障域；**控制面 quorum 按锁定版本要求**；重建能力 |
| 原件 | 对象存储（EC/副本，多站点） | 盘/节点/站点 | 原件不可读 | EC/副本 + 跨站点复制 + 版本化 |
| 计算 | worker 池按队列分组 | worker 主机 | 队列积压 | 多副本 + 队列分组 + 重建可抢占 |
| 模型 | 模型服务多实例 + 槽位闸门 | GPU/进程 | 对话与向量化停 | 多实例 + 队列 + 降级（§4.8） |

> **Redis 隔离口径**：不同 DB 号只是**键空间隔离**，实例的内存/CPU/网络/持久化仍共享，**不是资源隔离**。

### 3.3 多节点下界：**按维度分别推**，不得按总字节定节点数

| 维度 | 下界公式（示例） | 说明 |
|---|---|---|
| 磁盘 | 见 §2.7 逐层校验 | 对象/PG/向量/暂存**各自**算，不可互换 |
| RAM | `Σ(常驻工作集) + page cache 目标 + PG shared_buffers + 应用 RSS` ÷ 每节点 RAM | 常驻 = 量化向量（若 `always_ram`）+ HNSW 图 + 热集 |
| IOPS | `QPS × 每查询访问段数 × 每段页数 × (1 − 缓存命中率)` ÷ 每节点 IOPS | 冷缓存场景要用更差的命中率 |
| 网络 | `λ_orig×(1+复制系数) + 查询返回带宽 + 跨站点复制` ÷ 每节点带宽 | 摄取与复制会叠加 |
| 查询 QPS | **分片请求负载 = QPS × fanout**（每次查询实际扇出的分片数）÷ 实测**单分片 QPS** → 分片数下界。"单分片 QPS"**只在定向单分片测量时才成立**；**同一请求扇出更多分片 ≠ 线性提升吞吐**，必须实测**热点分片**与**读副本路由**的真实负载 | 不是按字节 |
| P99 | 由**扇出 × 冷缓存 × 量化**共同决定（§4.7、§10） | 需实测，不能用平均延迟推断 |
| 分片 | `Σ点数 ÷ 单分片点数上限`（上限由 RAM/构建窗口决定） | 超大租户可拆多分片，不可塞单热点分片 |
| **故障后重建窗口** | `重建字节 ÷ 可用带宽 ≤ RTO 预算` → **限制单节点容量上界** | 节点越大，重建越慢；这是"少而大"的反向约束 |

**结论（三条，缺一不可）**：

1. **逐资源池**取 max 下界并**向上取整**（对象盘 / PG 盘 / 向量盘 / 暂存盘 / CPU / GPU 显存 / 网络 / IOPS 各自算）；
   **不同角色的机器不可用一个全局 max 替代**——PG 节点、向量节点、worker 节点、代理节点必须各自选型。
2. **不能**用 `总字节 ÷ 单机盘容量` 直接得节点数。
3. **必须校验"丢一台主机之后"的状态**：剩余容量是否仍满足 §2.7、副本与**控制面 quorum** 是否仍成立、
   **重建期性能**（重建窗口内检索/写入的降级幅度）是否可接受 —— **只算稳态不算数**。

### 3.4 Qdrant 兼容与集合策略（锁定 1.15.5）

- **量化**：**int8 作为评估基线**；binary 等**仅在召回验证通过后**才作为选项；`always_ram`、`hnsw.on_disk`、
  `vectors.on_disk` 是**三个独立开关**，分别配置与实测（§5.7）。

  ①**点对账**（确定 ID/digest 的有界 `retrieve`，§8.2）与 ②**实际检索质量与延迟验收**（召回集 + P95/P99，§10.2）。
  三者都要，缺一不算达标。

## 4. 高并发设计

### 4.1 并发 ≠ 到达率

- **并发（in-flight）= 到达率 λ × 平均响应时间 W**（Little 定律）。"支持 N 并发"必须同时给 λ、W 与资源上限。
- 各类负载容量上限由**不同资源**决定，必须**分开预算**：

| 负载 | 决定容量的资源 | 独立预算手段 | 超限响应 |
|---|---|---|---|
| 上传/入库 | 对象带宽、暂存配额、worker CPU/OCR | 每用户/库字节配额、在途字节、独立 `ingest.*` 队列 | 429 / 503 / 202 |
| 列表/详情 | PG 连接、页缓存、偏移分页 | **游标分页**、短事务、连接池 | 429 |
| 检索 | Qdrant 扇出、PG、rerank CPU | 每用户 QPS、top-k 上限、超时取消、过滤下推 | 429 / 503 |
| AI 对话 | **模型槽位**、GPU 显存、上下文长度 | 槽位闸门、有限等待、输出 token 上限 | 429 / 202 |
| 后台重建/回填 | Qdrant 写入、PG 写、CPU | 独立队列 + 写入限速 + 时间窗 | 内部限速 |
| 审计写入 | PG 链头锁（当前全局串行） | 分链 + 批量 + 错峰（§5.3） | 内部 |

### 4.2 入口多副本、共享会话与超时分层

- **会话**：当前是 **DB 会话**（未设 `SESSION_ENGINE`）→ 多副本**不依赖粘性会话**，但每次请求读写主库；
  规划：会话迁 Redis，或保留 DB 会话但限制写频率；入口必须**无状态**。
- **超时分层方向**：**依赖超时 < 应用总 deadline < 代理总 deadline**（示例：依赖 10 s < 应用 300 s < 代理 310 s），
  留出取消传播与回执时间；队列侧另设可见性超时/租约（§4.4）。**SSE 的闲置超时与心跳单独设置**。
- **HTTPS / Cookie / 可信代理**（两件事，都要做）：`Secure` cookie 是否可用由**浏览器**按外部是否 HTTPS 决定；
  可信代理头（`SECURE_PROXY_SSL_HEADER` + `X-Forwarded-Proto`）的作用是让 `request.is_secure()`、CSRF 与
  `SECURE_SSL_REDIRECT` 判断**正确**；只做其一会分别导致重定向循环或 CSRF 失败（§9.2）。
- **故障摘除**：用 `/api/v1/health/ready/`（就绪）而非不存在的 `/api/v1/health/`。

### 4.3 上传：staging 直传 + 两阶段提交 + 验证作业

```
① 申请上传会话 → 建 upload_id（created→uploaded→verifying→published/failed）→ 返回 presigned URL(staging 前缀、限时)
② 客户端直传 staging（字节不经 web）
   # presigned URL 在过期前**可被重放**，不是"单次令牌"；大小/类型限制需 POST policy 或后端实际能力
③ 提交（upload_id + staging key + version_id + 自报摘要）→ **CAS 校验会话状态** → 绑定精确 version_id
   → 写"验证作业" → **返回 202**（不在 web 请求里做长耗时摘要重算）
④ worker：可信方式取得全文摘要 → 校验大小/类型 → 条件提交到内容地址（If-None-Match:*）
   → 写对象登记（含 version_id）→ 入 outbox → 会话置 published
⑤ 客户端轮询状态；**只有 published 之后**才对外可见（索引完成后再置"可检索"）
```

必须写死的规则：

1. **不信任客户端自报摘要，也不假设"URL 只能提交一次"**：用**会话 + 状态 CAS** 保证同一会话只受理一次；
   **绑定 `version_id`**；**最终提交幂等**——已 `published` 的会话再次提交必须被拒绝并返回既有结果。
2. **大小/类型限制**落到实际支持的方式（POST policy 或后端能力）+ 提交阶段复验；暂存配额计入 §4.4 在途预算。
3. **摘要取得不占用 web 请求**：大文件走**持久化验证作业**（202）；**multipart 的 ETag/复合校验值 ≠ 全文 SHA-256**。
4. **条件写覆盖 `PutObject` 与 `CompleteMultipartUpload`**，桶策略层禁止其他覆盖路径；明确 409/412 与遗留分片回收。
5. **staging 与最终地址分离**，短生命周期；提交失败可重试且幂等。
6. 直传不改变不可篡改语义：内容地址仍由**服务端**校验后的摘要决定（§6）。
7. **物理硬帽不能只靠 PG 会话**（容量验收条件）：直传 URL **可重放**、**版本化桶**下同 key 重复 PUT **会新增物理版本**，
   而 **PG 会话 CAS 约束不到对象盘字节**。硬帽必须由**实际对象写入端能力共同执行**：
   staging 唯一 key 的**条件创建**（`If-None-Match: *`，**兼容性实测**）、**multipart / 重试逐次预留**、
   并计入**未完成分片**与**全部未回收版本**（细则见 §2.6）。
   若目标 S3/MinIO 后端**无法强制约束**，**必须**改为**受控上传入口**或**其他可执行配额方案**；不得只在方案里承诺 PG 预留。

### 4.4 异步管道：独立队列 + 在途预算 + 有限等待 + 取消边界

- **队列分组**：`ingest.small` / `ingest.large`（OCR、Office、超大 PDF）/ `backfill`（回填）/ `reindex` / `maintenance` / `notify`。
- **在途预算（四维准入）**：字节（每用户/库在途 + 暂存占用）、页数（单文件与全局 OCR 并发页）、
  tokens（模型输入/输出，按日/按库）、模型耗时（槽位占用）。超限 → 429 或 202 排队，**不无限堆积**。
- **有限等待与取消边界**：
  - 每阶段硬超时 + 取消传播（显式取消、租约到期 → 停止下游并释放槽位）；
  - **客户端断开不取消已 202 持久接受的入库/回填/重建任务**（它们是持久事实，只能由**显式授权取消**或**状态机超时收敛**终止）；
    只有**交互式生成**（对话回答）允许在断开时放弃；
  - `KB_PROCESS_LEASE_SECONDS=900` 必须与长任务时长、队列可见性超时一起复核。
- **幂等**：上传以内容地址幂等；任务以 `(file_id, stage, generation)` 幂等；点 id 用 `uuid5` 可复现。
- **outbox 的保证范围**：只保证**业务数据与"派发意图"落在同一 PG 事务**（不会"记录已写但没人处理"）；
  **不保证** broker 派发是原子 all-or-none —— 派发是**至少一次**，需要消费侧幂等 + 回执重试 + 超时重投。
- **状态码语义**（区分"未受理"与"已持久受理"）：
  `400/409/422` 未受理（无副作用）｜`429 + Retry-After` 限流配额｜`503 + Retry-After` 依赖不可用可重试｜
  `202 + 状态资源` 已持久受理（不是"已完成"）｜`GET` 状态接口 **`200` + 明确 `status`（`pending`/`running`/`published`/`failed`）**。
  **禁止**用含糊的 `200`"成功"掩盖未完成状态。

### 4.5 配额与公平调度

- 每用户：并发上传数、日字节、在途字节、检索 QPS、模型 token/日。
- 每库：总字节、向量点数、回填/重建频率、模型 token/日（库管理员配额）。
- **公平调度**：按库加权，避免单库占满队列；超配额只降级该用户/库。
- 现状缺口：DRF 未配 throttle；`SlotLimiter` 只管模型槽位 → 每用户 QPS/字节配额是**新增能力**（不得因限流绕过权限检查）。

### 4.6 模型侧：批处理、多实例、显存预算、流式的定位

- **批处理**：`KB_EMBED_BATCH_SIZE=16`（受服务端 `max_num_seqs` 限制）。**维度 1024→2048 只确定"向量输出字节翻倍"（8192 B/点）**；
  **权重 / 激活 / 显存占用取决于具体模型、输入长度、batch 与精度（fp16/int8）**，**不能**由输出维度推出"整卡显存翻倍"；
  批大小与实例数必须按该模型的**实测基准**定（§2.9 的 `q_inst`）。
- **多实例 + 槽位（既有能力，勿当新增）**：`SlotLimiter` **已按 `service` 键隔离**（`ratelimit.py:179` 的 `_key`；
  已知服务集 `("embedding","rerank","ocr","llm")`；嵌入按 `embed:{profile}` 细分；`DEFAULT_LIMIT=4` 是**每服务**额度；
  熔断另有按服务键）。**规划项**是：按各服务**实例数**与实测容量设定每服务额度（区分交互/后台优先级）。
- **上下文与 KV 显存预算**（参数待填）：`每请求 KV ≈ 2 × L × H_kv × d_head × seq_len × dtype_bytes`；
  `并发上限 ≈ (显存 − 权重 − 激活余量) ÷ 每请求 KV`；chat 与 embedding **分开算**。
- **输入/输出边界**：超长**拒绝而非静默截断**（§8.3）。
- **流式的定位**：只改善体验（降低首 token 感知等待），**不提高**模型生成能力与并发上限；TTFT 与完整回答时间分别计量。

### 4.7 背压的容量关系

```
单类负载服务率 μ（实测）→ 建议准入上限 λ_max ≈ 0.7 × μ【验收建议·待确认】
队列年龄告警：P95 等待 > 目标值 → 加 worker，或明确拒绝
λ > μ 时排队发散：必须在越阈值前拒绝，而不是无限堆积
```

### 4.8 缓存优先与降级顺序

**缓存是常态手段**（不是降级手段）：缓存键必须含**用户授权域（含撤销 epoch）**、**库与数据代次（§7.2 manifest）**、
**模型版本**与查询参数；命中后按授权域**复核失效**，不得跨授权域复用。

**降级顺序**（先无损、后有损；**有损必须显式标注**）：
1. 暂停/限速**非关键后台**任务（回填、重建、巡检）（无损）
2. 缓存命中优先、合并重复查询（无损）
3. rerank → 关（**标注"未重排"**）
4. 稀疏路 → 关（**标注"仅语义召回"**）
5. 超大文件/长任务 → 转异步（202）并限速

**永不降级**：权限判定、审计写入、不可篡改校验、删除授权（三次确认）、**必要的原件完整性巡检**。

## 5. 优先消除的瓶颈

### 5.1 候选 ID 全量 `set`（`views.py:754`）
把结构化条件下推索引侧（Qdrant payload 过滤 + PG 有界 join/EXISTS），只把**有界**候选集交给检索；授权用库级 + 权限码表达；
对超大授权范围设**扇出上限**并在超限时明确拒绝或分批；**检索时复核授权**。

### 5.2 `text__icontains` 兜底（`pipeline.py:1750,1787`）
三条候选（必须实测后定，不得凭文档假设）：① PG FTS（`tsvector`+GIN，**中文需分词器/扩展**，官方镜像没有）；
② `pg_trgm`+GIN（中文子串；索引膨胀与短查询效率待实测）；③ 专用稀疏向量/全文索引。
**不变量**：中文分词、排序、过滤、重建、召回融合、**权限过滤**等价或更强；关键词回归集覆盖专名/编号/数字/中文短词。

### 5.3 审计全局锁（`audit/services.py:55-69`）
**分链**（按租户/时间窗口）+ **批量追加** + **外部锚定**（定期把链头哈希写入不可变存储）；保留"同链严格串行"这一必要性质；**不删锁**。

### 5.4 `verify_chain()` 全量入内存（`audit/services.py:91-93`）
改**游标/增量校验**（按 `id` 分批、可断点、记录位点），保留全量能力；**禁止**截断后当通过（结论必须标注校验范围）。

### 5.5 PG：连接池、短事务、只读副本与权限一致性
- **`CONN_MAX_AGE`（按 Django 6.1 官方文档）**：`CONN_MAX_AGE=0` 是 **ASGI**（应禁用持久连接）与
  **Django/psycopg 内置池**（`OPTIONS["pool"]` 时**必须为 0**，生命周期改用 `max_lifetime`）的要求；
  **外置 PgBouncer + WSGI 无此硬性要求**。本项目**主动选择**保守取值 0（与 ASGI/池化都不冲突，配 `CONN_HEALTH_CHECKS`）。
- **事务池化须单独验证**：① `DISABLE_SERVER_SIDE_CURSORS=True`（或 `atomic()` / 单独直连/session 池化）；
  ② **prepared statements 兼容性**（按池化器实际版本验证）；③ **事务局部治理授权**（`SET LOCAL`/会话级状态跨事务失效）。
- **短事务**：禁止在事务内做模型调用、对象存储 IO、长时间 CPU。
- **只读副本**：**读己所写**必须保证（写后短窗口走主库或按 LSN 等待）；报表/巡检读可走副本并**标注新鲜度**。
- **权限撤销一致性**：授权判定读主库或用带**撤销纪元**的缓存；撤销在有界时间内生效。

### 5.6 ASGI 与同步调用（必须验证）
现状是 **WSGI + 线程化 worker（`--workers 2 --threads 4`，gthread 语义；未显式 `-k`，需运行时确认）**，请求路径**同步阻塞**。
若改走 ASGI，**必须逐个验证**没有在 async 上下文直接跑同步代码（ORM/`httpx` 同步客户端/文件 IO），
否则 `SynchronousOnlyOperation` 或阻塞事件循环；确需同步就显式走线程池，并**压测证明**吞吐提升真实存在。

### 5.7 Qdrant：路由、热点、副本放置
- **路由**：同租户数据落**可预测**分片；超大租户可占多分片，不得塞单热点分片。
- **热点**：按库统计点分布与查询分布，给单分片设**点数与 QPS 上限**，超限即拆。
- **副本放置**：`replication_factor ≥ 2` 且**跨物理主机/故障域**；"同宿主多容器"不能证明丢一台机器仍可用。
- **版本兼容**：参数以 **1.15.5** 为准逐条核对（附录 A）。

### 5.8 反作弊红线
不删审计锁、不截断 `verify_chain` 结果并称"通过"、不跳过权限判定、不把"未索引"当"成功"、
不靠重建空库通过迁移验收、不把抽样校验当作全文摘要保证、**不用"点存在"或 `wait=True` 冒充"可检索"**（§7.3）。

## 6. 原件存储与不可篡改

### 6.1 BlobStore 抽象与逐对象登记
现状 `StoredBlob` 暴露 `Path`/`rel_path`/`read_only`（文件系统耦合），`rawstore.py` 是死代码。
目标：`BlobStore` 协议（`put_stream/open/exists/stat/delete/presign/iter_keys`），
`LocalBlobStore`（保留 `.part`+`os.replace`+fsync+只读语义）与 `S3BlobStore`；`storage.py` 保持现有函数名做薄封装。
**逐对象登记表**（PG）：`backend`、`bucket`、`key`、`version_id`、`sha256`、`size`、`state`（staging/committed/quarantined）、`verified_at`。
**兼容读路由**按登记表选后端，而不是全局开关。迁移工具 `kb_blob_migrate`（逐对象校验摘要、可断点、保留源、按库灰度）。

### 6.2 可信提交协议与摘要类型
摘要类型必须区分并登记：**全文 SHA-256**（内容地址依据）、传输校验值、multipart 复合校验值（**≠**全文摘要）。

### 6.3 版本化、Object Lock 与引用回收
版本化/Object Lock 保护的是**对象版本**，不阻止同 key 新版本或 delete marker；DB 必须记录**确切 `version_id`**。
受控删除：**先逻辑撤销**（登记 + 审计）→ 按引用计数与保留期**异步物理回收**；"复制到隔离前缀 + 删除"**不是**跨系统原子操作。
合规保留期内的版本**不能删除**：删除通道必须能表达"保留期阻止删除"（明确失败，而不是假装成功）。

### 6.4 迁移期与直传期对象可读性
三类对象（迁移前 / 迁移期新增 / 切换后直传）都要有读路径演练；区分**应用回滚 / 路由回滚 / 灾难恢复**三种"回滚"。

### 6.5 撤回"一键回落"
`KB_BLOB_BACKEND=local` 一键回落**不成立**（直传对象没有本地副本）；正确做法是 §6.1 的逐对象登记 + 兼容读路由；
若要"对象存储整体故障仍可本地读"，必须**双写/复制所有新对象**，并在复制完成确认前**不得宣告可回滚**。

### 6.6 治理红线不动
内容寻址、写一次、受控删除、`governance`（append-only、受控可变字段、行级触发器、受保护前缀/方法）、审计、权限全部保留；
新存储层**不得**绕过。

## 7. 元数据与向量

### 7.1 分区：`PRIMARY KEY(id)` 是硬障碍
PG 17 要求分区表的主键/唯一约束**包含所有分区键**，因此按 `file_id` 分区时**不能保留单列 `id` 主键**。
候选（必须实测后定）：① 复合主键 `(file_id, id)` + `UNIQUE(file_id, ordinal)`；② 独立标识映射（对外改用 `(file_id, ordinal)` 或 UUID）；
③ 维持单表 + 其他分层手段。
迁移必须覆盖并逐项验证：Django migration state、序列归属、外键、索引、**行级触发器在分区表上的行为**、删除授权、双写与回滚后的增量一致性；
且"表改名不会自动重绑依赖对象"。**口径**：64 个 HASH 分区仍在**单台 PG** 上 ≠ 分布式写入；按 `file_id` 分区**不能**按时间淘汰冷数据。

### 7.2 物理代次 + 不可变 manifest 一致读（2048 切换的落地方式）
- **一致读协议**：PG 保存**不可变 manifest**（`manifest_id`、`epoch`、`物理集合名`、`模型/维度/版本`、`分段策略版本`、状态）；
  **一次查询只解析一次 manifest**，随后**直接用该 manifest 的物理集合 + 对应模型**；请求内不再读任何可变指针。
  **切换 = 原子发布 PG manifest 指针**（单行单事务）；**alias 只作管理与兼容入口**（reconciler 跟随更新），**检索不读 alias**。
- **状态机**：
  ```
  PREPARE : 建新物理集合(2048) → 写 manifest(loading) → 灌数据并记录水位(watermark)
  MIGRATE : outbox 双写；按 watermark 追平 delta（删除 tombstone 同步到两代）
  VERIFY  : 覆盖率核验（**覆盖对象 = 全部"可处理资料"**；排除项须显式登记、不进"已完成"）：
            新代点数 ≥ 期望、逐段 digest 一致、维度/模型/分段版本匹配
  PUBLISH : PG 单事务把 manifest 指针切到新代（epoch+1）→ 检索立即改用新代
  SETTLE  : 在途请求按各自固定的 manifest 继续；双写窗口内两代都可读
  ROLLBACK: 同样以"发布 manifest 指针"回滚（不是切 alias）；旧代保留到在途完成 + 回滚窗口结束
  ```
- **必须定义**：各步宕机点与收敛方式；tombstone 两代同步；双写窗口边界与水位校验；共享集合的切换粒度
  （作用于**整个集合**，无法实现"库 A 独立切代而库 B 不动"——需按库拆集合或用 payload 版本字段过滤）。
- **验收**：换模型期间查询持续成功；**旧模型绝不读到新代向量**（专门的错配回归用例）；新增/删除不丢；跨库无串点。

### 7.3 HNSW 三态：LOADED / INDEXING / SEARCHABLE（**不得用点存在冒充可检索**）

| 状态 | 含义 | 可以对外承诺什么 |
|---|---|---|
| **LOADED** | 点已写入且可 `retrieve`（`wait=True` 只到这一步） | **只有"已写入"**，**不等于可检索** |
| **INDEXING** | 索引构建中（segment 优化中） | 只能提供**容量/性能观察**，不得作为检索达标证据 |
| **SEARCHABLE** | 索引构建**完成**，且通过**召回 + 延迟**核验（与基线对比） | 才可声称"可检索" |

规则：
1. **点存在 / `wait=True` / 集合总点数 / `indexed_vectors_count` / `optimizer_status` 都不能证明批次完成或可检索**；
   完成必须靠**确定点 ID/digest/代次的有界 `retrieve` 对账 + 持久化检查点 + 索引构建完成核验**。
2. **HNSW 构建策略按场景分**：**离线新建集合**（首次全量导入 / 换代重建）可**条件性**延后 HNSW —— 导入完成后**显式触发**并等待 `SEARCHABLE`；
   但**在线增量写入的生产集合不一律关索引**（否则查询质量与延迟不可控）。`wait=False` 必须另有该版本实际支持的完成证据，否则**不采用**。
3. **过滤索引（payload index）必须在批回填之前设计**，与查询模式一起定并按**锁定版本**验证（§3.4）；
   **不得**等全量导入完成后才决定是否重建索引——那时的重建代价与窗口都不可接受。
4. **不给超大未索引集合提供在线检索**（宁可排队/降级，也不给"看起来有结果"的假可用）。
5. **监控字段只作辅助**：1.17 时代的优化/监控字段在 **1.15.5** 上未必存在或语义不同，**不得**作为完成判据
   （判据是 §8.2 的点对账 + §7.2 的覆盖率核验 + §10.2 的召回/延迟实测）。

### 7.4 payload 字段与覆盖核验
**不能简单删 `text`**（`search_sparse()` 与 `_verify_collection_coverage()` 逐字比对都依赖它）。
替代：payload 保留 `chunk_digest`、`parser_version`、`chunk_strategy_version`、`model`/`model_version`、`library_id`、`file_id`/`ordinal`、`content_sha256`，
用**摘要比对**替代逐字比对，正文按授权回源；**前置条件**是 §5.2 的替代全文路径达标，**收益须扣除替代索引成本**。

### 7.5 计数与分页口径
**面向用户的展示计数**可近似/缓存但必须标"约"，不得用于权限或一致性判断；
**后台必要精确校验**（覆盖核验、删除对账、审计）**不得**用近似替代。
`count(exact=True)` 只应出现在后台校验路径并有规模上限与超时；交互路径改近似 + 缓存；分页统一改**游标分页**。

## 8. 摄取可靠性与资源边界

### 8.1 端到端状态机
```
对象提交(committed) → 元数据事务 + outbox → 派发(队列) → 解析 → 分段写盘 → 嵌入 → 向量写盘
                  → 索引构建 → 覆盖率/摘要核验 → SEARCHABLE
每阶段：幂等键、进度/游标、租约、超时、取消、失败隔离、可观测
```
必须定义：broker 不可用、发布成功但回执丢失、worker 被强杀、索引超时、重复投递、删除与重建并发、模型不可用、磁盘/暂存耗尽。

### 8.2 索引完成确认
`wait=true/false` 只改变**确认时点**；`wait=false` 的确认**不等于**可检索。
默认做法：`wait=True` 的**有界批写** + **有界 `retrieve` 对账** + **持久检查点**；再按 §7.3 等待 `SEARCHABLE`。
现状 `upsert(wait=True)` 与"有界批处理"可以并存——它**不是**"没有背压"的充分证据；改 `wait=False` 也不自动带来背压。

### 8.3 解析/OCR 的资源上界与超限语义
现状 `write_chunks` 接收 `list[ParsedBlock]`、`embed_chunks` 在**已物化列表**上分批（`MAX_BLOCK_CHARS=1200`、`MAX_BLOCKS=20000`、`ocr_pages` 默认 20）。
需要按格式定义**增量输出或页/段检查点**，并限制：单文件临时磁盘、解压比、页数、正文膨胀比、转换子进程、OCR 并发、总耗时。
**超限语义必须显式**：失败 / 部分完成（标注覆盖范围）/ 可续作 —— **禁止**把截断当"全文成功"。
自动"性质"识别涉及**逐文件模型成本**，纳入模型预算并沿用"人工结果优先"。

### 8.4 五个**独立**瓶颈（不能只算 GPU）
| 瓶颈 | 决定因素 | 观测指标 |
|---|---|---|
| 对象存储写入带宽 | 摄取 GB/s（§2.8） | PUT 吞吐/延迟、错误率 |
| 对象存储读取带宽 | 解析回读 + 重建 | GET 吞吐/延迟、冷读 |
| **PG WAL 写入** | 分段写盘 + 元数据更新 | WAL 速率、checkpoint、锁等待 |
| **HNSW 构建** | 点数、维度、m/ef、CPU+IO | 构建点/s、构建窗口、`INDEXING→SEARCHABLE` 时长 |
| **OCR 页吞吐** | 页/s、CPU / **GPU** / 子进程 / 临时盘 / 模型实例（**视觉 OCR 可能与嵌入共享实例与显存**，须按实际资源池隔离预算） | 页/s、单页耗时、超时率、与嵌入并发时的相互影响 |

任一项先到上限，整批完成时间就由它决定——**端到端口径（§2.9 B）**必须逐项测。

## 9. 服务器部署、HA 与可恢复备份

### 9.1 分层门槛
T1 首台 Linux 试运行（可交付、可复现、可恢复，明确容量与故障恢复上限）；T2 在 T1 门槛全过 + §10 压测达标 + RPO/RTO 演练通过后进入。

### 9.2 服务器安全基线
| 项 | 要求 | 现状/差距 |
|---|---|---|
| TLS 与入口 | 代理终止 TLS，仅入口开放端口 | **无代理**；容器端口直接发布 |
| 可信来源 | `X-Forwarded-Proto` + `SECURE_PROXY_SSL_HEADER` 成对，只信任代理 IP | `SECURE_PROXY_SSL_HEADER=null`（事实） |
| Cookie 安全 | `SESSION_COOKIE_SECURE=true`、`CSRF_COOKIE_SECURE=true`（HTTPS 生效后） | 均为 false（本地 HTTP 模式事实） |
| 域名与 CSRF | `ALLOWED_HOSTS`、`CSRF_TRUSTED_ORIGINS` | 现仅 `127.0.0.1,localhost,testserver` |
| 凭据 | 全部外置、可轮换 | 【待填参数】 |
| 权限与卷 | 非 root、卷 UID/GID、临时盘与资源限额 | compose 无资源限制 |
| 日志/监控 | 轮转 + 集中收集 + 队列年龄/错误率/延迟/磁盘水位告警 | 【规划】 |
| 网络 | 组件分段，只允许必要路径 | 【规划】 |
| 依赖可重建 | 离线可重建、版本锁定与校验 | 已锁（附录 A） |

> 服务器入口启用 HTTPS 时两件事要**分别**做（§4.2）：①浏览器侧按外部 HTTPS 决定是否发送 `Secure` cookie；
> ②应用侧配置可信代理头让 Django 的 `is_secure()`/CSRF/重定向判断正确。只做其一会分别导致重定向循环或 CSRF 失败。

### 9.3 备份、PITR 与恢复顺序
- **PG**：基础备份 + **连续 WAL 归档**（PITR），不是"按分区 dump"；备份账户隔离、可校验、**定期恢复演练**。
- **对象**：版本化 + 跨站点复制；**对象清单（登记表）与对象本身分别备份**，恢复时先清单后对象再校验摘要。
- **向量**：可重建，但**"可重建"≠"能在 RTO 内重建"**；按 §2.2/§8.4 估算 HNSW 构建耗时并演练。
- **恢复顺序**：① PG 元数据（含清单与 manifest 登记）→ ② 对象原件 → ③ 向量（重建或快照）→ ④ 缓存/会话 →
  ⑤ 校验（覆盖率、摘要、权限、审计链）→ ⑥ 放量。

### 9.4 RPO/RTO（**验收建议·待确认**）
| 项 | 建议基线（待确认） | 演练要求 |
|---|---|---|
| RPO | ≤ 15 分钟 | 从 WAL 归档恢复到指定时间点，核对最后可见数据 |
| RTO | ≤ 4 小时（单站点） | 空机恢复 + 校验通过 |
| 复制/切换 | 主备自动切换 + 防双主 | 主机失效 + 切换后权限与审计校验 |
| 向量恢复 | 按 §2.8/§8.4 估算 | 从对象重建一批并核对点数/摘要/`SEARCHABLE` |

> **"无数据丢失"的口径**：RPO=0 **只在该故障域内存在合格同步副本/仲裁、且提交在返回成功前已同步持久化到它**时才可声明
> （PG 默认**异步**，见附录 A）；`remote_write` 只到备用 OS，**不得**据它声明零丢失。
> 该保证**只覆盖"在约定故障模型下仍存活、且已持久确认的合格同步副本"**；**错误提升落后副本、同步降级、配置错误、
> 超出约定故障模型的情形均不在零损失保证内**，必须用**切换策略与故障演练**验证。
> **PG 的确认不能替代对象/向量各自的确认**；"已受理"与"可检索"是两个状态（§4.4、§7.3）。

### 9.5 上线门槛（基础备份不得推迟）
1. PG 基础备份 + WAL 归档**已运行**且**已成功恢复过一次**；
2. 对象存储版本化/生命周期就位，"删除被保留期阻止"的分支被测过；
3. 密钥外置、仅入口开放端口、Cookie/代理成对；
4. 监控告警覆盖：队列年龄、错误率、P95/P99、磁盘水位、备份失败、租约过期、**索引构建/`SEARCHABLE` 状态**；
5. 以上任一缺失，**不允许**以"等有数据再补"为由上线。

## 10. 压测与验收矩阵

### 10.1 方法论
报告必须含：**并发（in-flight）、到达率 λ、响应时间 W** 三者关系（Little 定律）与资源读数（CPU/RAM/IOPS/网络/连接/队列年龄）。
每类负载单独出 λ→W、λ→错误率、λ→资源曲线，给出拐点与建议 `λ_max`。目标数字一律标"**验收建议·待确认**"。

### 10.2 指标清单
| 类别 | 指标 |
|---|---|
| 检索 | QPS、P50/P95/P99、冷/热缓存、召回率、过滤选择率、扇出分片数 |
| 对话 | QPS、**首 token 时间**、**完整回答时间**、tokens/s、槽位等待、超时率 |
| 摄取 | 文件/min、原件 MB/s、**解析段/s**、**嵌入段/s**、**OCR 页/s**、各阶段耗时、失败与重试率 |
| 索引 | 写入点/s、**构建点/s**、`INDEXING→SEARCHABLE` 时长、段数、优化状态 |
| 队列 | 队长、**队列年龄 P95**、租约过期数、死信数 |
| 存储 | 对象 PUT/GET 吞吐与延迟、PG 连接等待、WAL 速率、锁等待、Qdrant 写入延迟 |
| 一致性 | 检索新鲜度（写入到可检索时长）、覆盖率核验结果、审计链校验位点 |

### 10.3 场景矩阵（**500 TB / 2048 只是输入参数**）
| 场景 | 目的 | 通过判据（待确认） |
|---|---|---|
| 单类负载基线 | 找每类 μ 与拐点 | λ→W 曲线稳定可复现 |
| **混合负载** | 上传+检索+对话+回填同时 | 无饥饿；交互类 P95 不因后台任务翻倍 |
| **索引构建共存** | 构建期仍服务在线检索 | 构建限速生效；P95 稳定；未 `SEARCHABLE` 的集合不接在线流量 |
| 冷缓存 | 清空页缓存后首轮 | P99 劣化在可接受范围，不雪崩 |
| **主库/ broker / LB 失效** | 停 PG 主库（触发切换）/ 网络分区 / 停 Redis broker / 停入口代理 | 无双主；分区宁可拒写；broker 恢复后 outbox 重放不丢；剩余代理仍可服务 |
| **权限撤销** | 撤销后立即检索 | 有界时间内不再召回；缓存不越权 |
| **中途取消与重投递** | 取消/重投递同一任务 | 幂等，无重复分段/向量；状态可收敛 |
| 故障恢复 | §9.3 恢复顺序 + PITR | 达成 RPO/RTO；恢复后权限与审计校验通过 |
| 长稳（≥8 h） | 内存/句柄/队列无泄漏 | RSS 与句柄平稳 |

> "无数据丢失"按 §9.4 口径表述；未确认的在途请求允许失败，但必须返回**明确错误**而不是静默丢失。

### 10.4 明确不承诺
- **没有服务器规格、增长曲线与 RPO/RTO 之前，不承诺"千并发/万并发"**，也不给采购数字。
- **不以小规模替代 500 TB 结论**：局部基准必须写明外推假设、误差与失效边界。
- 实测数字一旦产生，必须附命令、镜像摘要、PG 真实实例信息与原始输出，**不得虚构**。

### 10.5 功能回归证据要求
回归基线必须附**对应源码/镜像摘要 + 真实 PostgreSQL 结果**，**跳过与通过分开统计**；版本控制有助于 diff，但**不等于能力验收**。

**停机窗口**：分区/主键变更、manifest 发布边界、应用不兼容变更、对象批次迁移切换点都可能需要短暂停写窗口，**按演练结果决定**。

### 12.2 保守决策规则
1. **容量**：按上界设计（小 `s̄`、高 `c`、`r_p=r_v=1`、去重 0、`G` 含新旧两代），宁可高估。
2. **吞吐**：只承诺实测值；未实测前只给公式与"拒绝优先于堆积"。
3. **恢复**：先建"能恢复"（T1），再追"恢复得快"（T2）；RPO/RTO 未定前按 §9.4 建议值演练。
4. **迁移**：一律先在副本演练；正式库操作必须"备份可恢复 + 回滚脚本 + 演练记录"三件齐备。
5. **选型**：先选可逆的（存储抽象、逐对象登记、游标分页、manifest），后选不易逆转的（分区分片拓扑、供应商）。
6. **固定目标不得自动降级**：**禁止**以"降回 1024 / 截断维度 / 只向量化热数据"来满足预算；覆盖目标始终是**全部可处理资料**，冷热只决定缓存/驻留层与回填顺序（§0.4）。

### 12.3 外部服务与拓扑：条件化选项，不替用户决定
| 选择 | 成立条件 | 代价/风险 | 必须实测 |
|---|---|---|---|
| 自建 MinIO | 自有硬件与运维能力、内网带宽充足 | EC/扩容/升级/多站点与值班 | EC 与单盘失效恢复、S3 子集（条件写/multipart/版本化/Object Lock/生命周期） |
| 云对象存储 | 接受按量计费与出口/取回费 | 请求/取回费用、供应商锁定 | 条件写与校验算法、版本化/Object Lock、生命周期与分片回收 |
| 单 PG + 分区 | 首年写入与恢复窗口可承受 | 写不横向扩展 | 分区裁剪、VACUUM/索引维护、PITR 演练耗时 |
| 分布式 PG | 单主库写入/WAL/恢复窗口实测不满足 | 事务/约束/触发器/迁移复杂度上升 | 事务与约束兼容、触发器、跨分片唯一性、扩容迁移 |

本版**不**给出采购或供应商结论，也**不**要求用户先回答任何选择题才能继续——参数缺失时按 §12.2 保守推进。
