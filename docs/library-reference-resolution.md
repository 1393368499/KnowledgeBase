# 对话中的信息库名称兼容

2026-10-28 用户实测将“合同档案库”称为“合同资料库”，模型把这个中文名称直接放入只认 code 的参数，导致搜索/列资料提案失败。另一次语音识别出的普通词“文达”也被模型当成库名。

现在 `list_files` 与 `search_knowledge` 在创建操作前解析用户叫法：优先保留精确 id/code 的身份，其次正式名称；再对常见资料库、档案库、知识库等容器后缀归一化，按业务主题选择唯一的可读候选。业务限定词不删除，不用编辑距离猜测。候选只来自当前权限与检索范围；多个候选明确列出供选择，不能自动挑一个。精确名称指向范围外的库时，仍按原目标拒绝，不能改指范围内的相似库。

模型收到当前账号可访问的真实库名/code 目录。未知的只读库名错误会回填到有界工具回路，允许使用目录纠正一次或多次（总轮数仍受原配置限制）；歧义不自动消除。已成功纠正的中间失败保留在工具调用历史，不再作为本轮失败提示。写入和删除的目标解析、权限和删除确认流程保持原规则。

统计整库并生成报告时，模型先取得真实文件清单，再以其中的文件 id 明确选择生成来源。现有来源覆盖检查和长文档分批整理继续生效，不把少量搜索命中当成完整统计。

验证：62 项 SQLite 相关回归通过，真实 PostgreSQL 的 28 项名称/范围测试通过。覆盖合同资料库/档案库/合同库/合同叫法、精确 code、真实工具调用路径、歧义、权限、检索范围、不能把删除改指相似库，以及识别错误名称后的有界工具纠正。线上原会话 #77 的最新请求在确认之前无任何已执行操作后，沿用原用户消息 201 恢复；真实清单 47 份，撰写操作使用 47 个不重复的合同档案库文件 id。

恢复结果：47 份资料共 1269 段，分 12 批处理后保存文档 #42。最终模型摘要超时，不重放已完成的文档操作。已核对真实清单，并将报告修订为口径明确的文件统计：47 份PDF，文件名年度标识2025为30份、2026为17份；不将未核验的签章、客户主体和金额当作统计结论。AI原始草稿保留在本机私密备份中。原会话补充明确的系统完成通知，原用户消息不重复创建，语音任务恢复为answer_ready。
