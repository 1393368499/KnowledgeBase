# 1024 → 2048 嵌入模型切换运行手册（当前 1024，2048 仅预留）

> **一句话口径**：**当前线上运行 1024 维**（profile `bge1024`，已实测）；**2048 仅"预留 profile"**，
> 待真实模型端点配置并验证通过后，才按本手册"验证 → 重建 → 受控切换"的流程上线。
> **不要**把 2048 写成已上线，也不要把本手册当成"500 TB 整体架构已实现"的证据。

## 0. 角色与前置

| 项 | 要求 |
|---|---|
| 权限 | 系统管理员（模型配置查看/探测、代次操作都是管理员面） |
| 备份 | **必须先有"已成功恢复过一次"的 PG 基础备份 + WAL 归档**（上线门槛，见方案 §9.5） |
| 影响面 | 切换期间**该库写入被冻结**（上传/解析分段/增量嵌入显式拒绝，HTTP 409 + `code=write_frozen`）；检索**只有在该代模型服务仍可用时**才不受影响 —— 模型服务停了，对应语义分组就只能按组降级为关键字检索 |
| 回滚预案 | 切换后若**有新数据写入**，直接回滚旧代会因**覆盖不足**被安全拒绝（见 §4） |
| 旧模型服务 | 换代/回退窗口内**旧模型端点与旧 model_version 必须保持可服务**：旧索引保留的只是向量数据，**查询向量（稠密检索要先用旧模型编码 query）与增量写入都依赖旧服务**；旧服务停了只能按组降级关键字 |
| 后台改动 | 索引登记（`VectorCollection`）与库的三个向量指针/编号字段在 Django admin 里是**只读**的；换代/回退只能走 `kbrebuild` 或受控意图，不能手改 |

## 1. 配置（不改代码）

- 预留 profile `bge2048` 的字段：`model`、`model_version`、`base_url`、`dimension=2048`
  （经 `KB_EMBED_PROFILES`（JSON 覆盖，**键必须在白名单内**）或 `MODEL_SERVICES["embedding"]`）。
- **配置严格性（运行期强制）**：未知 profile 名、未知字段、非法维度、**覆盖 `name`** 一律显式报错；
  未配置（model/base_url 为空）是合法状态但**不等于就绪**。
- **禁止**：把 2048 声明成 1024 的"升级"、补零、截断、或声称"2048 已就绪"。

## 2. 验证（切换前必做）

```bash
# 只读探测：允许探测**非当前**的已配置 profile（白名单，不接受任意 URL）
GET /api/v1/knowledge/models/?probe=1&profile=bge2048
# 或 CLI（等价路径）—— **必须带 --probe 与 --service embedding**：
# 不带 --probe 时 kbprobe 只打印配置、不发起任何真实调用；
# 不带 --service 时探测的是默认服务集合，不是嵌入 profile。
python manage.py kbprobe --probe --service embedding --profile bge2048
```

判定标准（缺一不可）：**实测维度 == 声明维度（2048）**、`model/model_version` 与配置一致、
延迟与批吞吐有记录、中文召回有抽样结论。**未通过就停在这里**，不要进入重建。

> 系统配置页的「嵌入模型 profile」表也可做同样的事（每行一个「预检」按钮，
> 只对**已配置**的 profile 可点，回报**实测维度**）；未配置的 profile 不能预检，
> 页面也不会主动探测。

## 3. 重建与受控切换

```bash
python manage.py kbrebuild --library <库code> --profile bge2048
```

内部顺序（代码强制）：**冻结本库写 → 新物理代次 → 复用只读分段全量重嵌入 → 覆盖率核验
（点数/维度/模型/摘要）→ 单事务发布 manifest 指针 → 解冻**。

- **`kbrebuild --profile <X>` 永远分配一个全新的代次**（编号严格单调、绝不复用），
  不会"就地补齐"任何已有代次。要换回某个模型，就是**用它重建出一个完整的新代**再激活。
- **失败/部分成功**：**不激活**，旧代继续服务；目标代次标 `failed` 并留 `build_error`
  （远端集合**不删**：里面可能已有真向量，删它是破坏性动作；该代已被登记为 failed，
  既不会被激活、编号也不会被复用）。
- **活跃租约冲突**：本库有正在解析/嵌入的资料时**重建被拒绝**（不抢占旧 job，不丢任务）。
- **冻结期内只有本次重建自己能发布**：外部激活/回退（含 planner 受控意图）在冻结窗口内
  一律被拒（HTTP **409** + `code=write_frozen` + `retryable=true`）。
- **崩溃残留冻结的安全恢复**（`kbunfreeze`）：
  1. **先确认旧 worker 已停止**（`kbprocess`/celery 队列无该库在跑、`parse_lease_expires_at` 已过期）；
  2. `python manage.py kbunfreeze --library <库code>` 只读打印**冻结原因/操作者/时间**
     （**当前不打印令牌**）；
  3. 确认该重建**已终止且不打算续跑**后，加 `--yes` 解除；解除的动作是
     **清冻结状态 + 再旋转一个新令牌**（不是"保留原令牌"）。因此**旧重建 job 的令牌**
     与**冻结前那些普通 writer 手里的令牌**都一并失效：即使"冻结→解除"期间
     collection 名字没变，旧 job 醒来后也会在 `assert_fence` / 写回校验处被拒绝。
  4. **审计口径（别夸大）**：`kbunfreeze` 当前**不自动写审计事件**，也不打印令牌；
     "谁、何时、依据什么判断旧 job 已停"需要**人工另行留痕**，解除后请复核闸门状态。
- 旧代次**保留可回退**（登记行与远端集合都不删）。
- **旧索引保留 ≠ 旧模型服务自动可用**：保留的只是**向量数据**。旧模型服务
  （旧端点与旧 model_version）**停了之后，这一代的语义检索立刻不可用**——
  因为**查询向量也要由这一代的旧模型现算**（检索不是"只读已存好的向量"：
  稠密检索必须先用该代登记快照里的模型把 query 编码成同维向量，再拿它去查集合）。
  一并受影响的还有旧代的**增量写入**。
  - 旧服务停掉时的**实际后果**：该代所属的**语义分组被按组降级为关键字检索**
    （`report.dense_groups_skipped` 会列出被跳过的分组、界面显示"部分结果"），
    健康分组继续跑 dense；**不能说"检索不受影响"**。
  - 所以换代/回退窗口内要么**保留旧模型服务可服务**，要么明确接受"旧代只剩关键字"。

## 4. 回退（重要限制：**不是无条件一键回退**）

- **切换后若旧代次没有新增数据的向量**（新代构建期间/之后又有文件入库），**直接回滚会被安全拒绝**：
  `rollback` 的覆盖核验发现"旧代的点数 < 当前应有"，即旧代覆盖不足。
- 正确做法（当前**只有第一条是已实现的**）：
  1. **用旧模型重建一个新的完整代并激活**（已独立验证）：
     `python manage.py kbrebuild --library <库code> --profile bge1024`，
     它会分配**新编号**、把当前全部未归档资料重新嵌入这一代、覆盖率核验通过后原子激活。
     **不要**把这条写成"补齐旧代次后再回退"——`kbrebuild` 不会补齐任何已有代次。
  2. ~~可验证的双写~~：**这是未来设计，当前没有实现**。现在不存在"一次写入同时落两代并被
     双重核验"的路径，所以不要按"双写后再切回"操作。回退与冻结期内都不接受外部发布，
     唯一受控路径是上面的重建 + 激活。
- 因此**不能承诺"无条件一键回退"**；回退前必须看清"旧代是否覆盖了切换后的新增数据"。

## 5. 版本与兼容边界（不要静默屏蔽、不要随意升级基础设施）

- 已实测组合：**qdrant-client 1.19.1 ↔ Qdrant server 1.15.5**（客户端版本跨度较大）。
  实际调用走的是**通用接口**（collection/upsert/retrieve/search/count），链路已验证；
  客户端会出现版本跨度告警，属**已知兼容边界**——**保留告警、记录版本**，
  **不要**用屏蔽告警或升级服务器来"消音"；若未来要用 1.16+ 新参数（如 `memory=cold` 等），
  必须在**锁定版本**上逐项实测后再引入。
- PG：`synchronous_commit=on` + `synchronous_standby_names` 非空才有 RPO=0 的前提；
  `remote_write` 只写到备用 OS，不足以声明零丢失（详见方案 §9.4 / 附录 A）。

## 6. 500 TB 示例口径（**只是示例，不是已实现容量**）

> 示例假设：500 TB 待处理原件、平均 5 MB → **1 亿文件**、每份 **50 段**（50 亿点）。

| 场景 | 单副本单代 | 两副本 | ÷0.7（留 30% 空闲） |
|---|---|---|---|
| 当前 **1024** | 26.24 TB | 两副本两代 **104.96 TB** | **149.94 TB** |
| 未来 **2048** | **51.84 TB** | 两副本两代 **207.36 TB** | **≈296.23 TB** |
| **1024 旧代 + 2048 新代各 2 副本并存** | — | 52.48 + 103.68 = **156.16 TB** | **≈223.09 TB** |

- 并存口径 = 1024 两副本**单代** 52.48 TB + 2048 两副本**单代** 103.68 TB。
- **额外项另计**：payload/过滤索引、稀疏索引、WAL/日志、快照、构建临时、备份、审计。
- **不得**把上表写成"已实现的 500 TB 架构"或"2048 已上线"。

## 7. 当前状态（本轮交付口径）

- 代码侧已实现：按代次**快照固定**绑定模型（查询与增量写入都不回落全局 active profile）、
  快照指纹缓存键、配置白名单/非法维度/`name` 覆盖拒绝、响应校验（条数/index 序/NaN/真实维度）、
  **库级写冻结 + fencing + 冲突拒绝**、**重建状态隔离**（重建不污染当前 file 状态）。
- **闸门覆盖全部真实写入口**（不只是 HTTP 入口先查一下）：
  - 上传建记录 / 写分段 / 增量嵌入 / 领取解析租约 / 索引初建发布第一代，
    都在**自己那个外层事务**里先过 gate（锁序固定 `gate → library`）；
  - **激活与回退**：`activate_generation` 默认路径必须过 gate；冻结期内外部激活/回退
    一律 409。只有**本次重建自己**能带着它的冻结令牌发布（同一事务内校验仍是当前 owner）；
  - 受控**归档**：状态复查 + 无活跃租约校验 + 精确远端删点 + 状态提交在**同一把 gate 锁**下，
    已冻结时**一个远端删点都不会发生**（不再有"点已删、归档却被拒"的中间态）；
  - 受控**删除/整库重建/恢复归档**：同样先过 gate。
- **许可贯穿模型 IO**：非重建嵌入在锁外做模型推理，但"许可令牌 + 活指针 + 租约"在
  **写点之前**与**状态提交时**各校验一次（含空 pending 的情况）；成功与**失败**
  （`partial` / `unavailable`）写回都走同一把许可。因此"冻结→解除后 collection 恰好没变"
  这种旧 job 复活场景也会被拒绝。
- **陈旧任务冲突**（`WriteFrozen` / `StaleGeneration` / `LeaseLost`）**不写 FAILED**：
  它们只终止本次写入、留一条审计，并原样上抛（HTTP 409 / 明确错误），
  不会把一份正常资料标成失败，也不会覆盖新 owner 的结果。
- **按完整快照指纹分组熔断**：熔断键是 `embed:<名>#<SHA256(规范 JSON 快照指纹)>`，
  同名不同端点/版本的两套嵌入服务**互不牵连**；搜索侧逐组降级，
  `report.dense_groups_skipped` / `dense_groups_queried` 如实回报，
  不再"一个模型坏拖垮全局"。
- **Django admin**：`VectorCollection`（索引登记）设为**只读**（不可新增/编辑/删除，仍可查看）；
  `KnowledgeLibrary` 的 `vector_collection` / `active_generation` / `next_generation`
  三个指针/编号字段设为 `readonly`；名称/级别/部门/客户/启用状态等**普通目录字段仍可编辑**。
  要换代/回退必须走 `kbrebuild` 或受控意图（带冻结、覆盖率核验与审计）。
- **测试隔离**：`knowledgebase/test_settings.py` 默认 `KB_MODEL_LIMIT_ENABLED=False`（生产配置不变），
  单测不会经 `SlotLimiter` 触碰共享 Redis 槽位键；需要验证真实限流的用例显式启用，
  并使用独立地址/前缀（或 FakeRedis）。
- 真实 2048 模型**尚未部署**；隔离环境用**替身**验证过完整链路（重建→查询→增量写入→回退），
  **替身结论不得当作真实模型验收**。
- **旧索引可回退的前提**：保留的只是向量数据。**查询向量与增量写入都依赖该代的旧模型
  服务**（稠密检索要先用旧模型编码 query）。旧服务停掉时，该代只能**按组降级为关键字
  检索**（`dense_groups_skipped`），不能声称"语义检索不受影响"；保留索引也不会让已下线的
  旧模型服务自动恢复。
